# A 5,205-vertex Dragon: prepared pictures and a C64 copying runtime

Research date: 8 November 2026. The published metallic Stanford Dragon
cartridge from [c64-3d-toolkit](https://github.com/FlyingFathead/c64-3d-toolkit)
contains **128 independently encoded pictures**. An independent decoder
matches every bitmap and screen byte against the project's supplied host
oracle: **128 × 8,640 = 1,105,920 bytes**, zero differences.

The selected C64 path copies literal bitmap spans and absolute screen-color
bytes. Its large model count describes the host input, not thousands of
vertices transformed by the 6510 each frame. This is a concrete example of
trading ROM capacity and host preparation for inexpensive C64 playback.
It is a separately published graphics-toolkit example, not an identified
part of Tower Power, Spires, or another demo in the existing investigation.

## From cartridge packets to actual runtime tables

The 361,216-byte CRT has hardware type 32 and 44 CHIP packets, each with
8,192 data bytes and chip type 2. There are 43 ROML banks and one ROMH bank.
The decoder reconstructs the bootstrap input's address placement from ROML
banks 0–2. The ROMH boot instruction `LDX #$58` specifies 88 pages, covering
`$0800..$5FFF`; the last bank's zero padding for `$6000..$67FF` is not copied
or used by the proof. The decoder reads the seven actual frame-directory arrays through the
published label addresses. Every frame's bank, source address, length and
metadata length agrees with the manifest; every frame-block SHA-256 agrees.
No frame crosses its 8 KiB ROM window.

These directory checks bind the manifest to concrete cartridge bytes; they
do not prove that a CPU completed the bootstrap or used those tables.

Three instruction fragments also match the cartridge's bootstrap bytes:

| Runtime label | Address | Matched bytes | Meaning |
|---|---:|---:|---|
| `v3_color_copy` | `$0A3D` | 9 | Copy absolute screen bytes through indirect pointers |
| `v9_group` | `$42BD` | 44 | Eight unrolled literal byte copies, then count/branch |
| `hors_v2_span_mapped` | `$428B` | 14 | Read destination and mask the high byte with `$1F` |

This is a 67-byte mechanism binding, not complete source-build equality or
native execution. The `$1F` mask matters: bit 7 in a span's high byte is a
cartridge-mapping release flag, not part of the bitmap address.

## Independent reconstruction of every prepared picture

Each decoded picture contains a 320×192 hires bitmap, **7,680 bytes**, and
its **960 screen bytes**. Borders, HUD and the remaining eight display lines
are outside this comparison.

The cartridge decoder reads clear metadata, the absolute color values,
the literal-span count, and each destination/length/data group. The separate
oracle path reconstructs pixels from the supplied vector records using
absolute coordinates and prefix counts of their step bits. It then applies
the oracle's resolved screen-color spans. It does not import the upstream
decoder or replay its DDA loop.

All **1,105,920 bytes** match. Both concatenated outputs have SHA-256:

```text
d3b0b9ed42874c0dbaf0d6189f7e96f34181feb1b35341a3e476120044e1a4e9
```

The supplied OBJ independently contains **5,205 vertices**, **11,102
triangles**, and **15,796 unique undirected edges**, matching the asset's
metadata. These counts do not establish correct projection or visibility.

| Prepared data | Per-picture range | Total over 128 pictures |
|---|---:|---:|
| Complete encoded block | 1,560–2,497 bytes | 279,935 bytes |
| Metadata | 492–516 bytes | 64,107 bytes |
| Literal bitmap spans | 22–48 | 4,475 |
| Literal bitmap bytes | 982–1,894 bytes | 202,147 bytes |
| Included zero bytes | 85–268 bytes | 25,183 bytes |
| Mapping-release flags | 12–25 | 2,395 |

The encoded stream intentionally includes some zero bytes between nonzero
regions. Copying a slightly larger contiguous span can avoid another setup
and mapping change. The source's `180 + 15 × length` batching budget is a
**host cost model**, not a measured interrupt-latency guarantee. No timing
measurement or comparison against our live Pong renderer was performed.

There is also a conditional static lower bound. Each literal byte passes
through `LDA (zp),Y`, `STA (zp),Y`, and `INY`: at least **5 + 6 + 2 = 13 core
cycles** on an ordinary 6510. A 1,894-byte picture therefore needs at least
**24,622 core cycles for these copy instructions alone**. Page crossings,
branches, mapping/setup, clearing, colors, IRQs and VIC stalls add work.
This assumes that the published path copies that picture once. It is not a
native cycle observation, frame-rate measurement, or acceleration claim.

The manifest's `runs` field counts **host-oracle vector records**, not the
literal spans copied by this C64 path. Here there are 134,166 such source
records, versus 4,475 encoded copy spans. Conflating these counts would
misdescribe the runtime work.

## Absolute colors remove one reset; bitmap clearing still matters

The actual bootstrap has **23 shared address runs**, covering **437 screen
cells**. Every picture supplies 437 absolute screen bytes, including base
values where an old object's color needs removal. Every nonbase color in
all 128 oracle images lies within this common address set. Thus the color
transport does not depend on which earlier picture occupied a buffer.

Each picture's clear metadata also covers every nonzero byte in its own
bitmap. A recycled slot must use the metadata for the picture it previously
held. Independent pictures do not eliminate that requirement. As a concrete
control, copying frame 1 over frame 0 without clearing leaves **37 incorrect
bitmap bytes**. The HUD and initialization contract remain outside this
bounded picture-data proof.

The useful distinction for our experiments is specific: absolute new color
values can replace old-color reset work when the new update covers the
complete union of changing cells. Bitmap pixels outside new literal spans
still need clearing. A prepared finite rotation also cannot supply arbitrary
Pong gameplay states without an additional live overlay or renderer.

## Replay and next evidence

```sh
rtk proxy python3 research/host3d/inspect.py
```

The [producer](../../research/host3d/inspect.py) uses the Python standard
library. Its receipt is `build/research/host3d/analysis/host3d-proof.json`.
The directory also retains both complete picture streams and a reconstructed
frame-0 PNG. The PNG uses an illustrative RGB palette; all proof comparisons
use original bitmap/screen bytes, not screenshot colors.

Native publication, bank mapping, IRQ behavior, physical hardware, frame
pacing, and upstream benchmark numbers remain unchecked. A next native
case should start the exact CRT naturally, record completed buffer
publication, bind the actually presented bitmap/screen pair, and measure
rendering separately from deliberate frame holds. Reproducing the host
geometry pipeline is a different next step; the published host oracle is
reference data, not proof that that pipeline itself is correct.
