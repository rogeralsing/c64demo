## The video lead is real; its technical contents remain unrecovered

Martin Piper's [ending teardown](https://www.youtube.com/watch?v=Vfnyczaf1Ao)
is an uploader-authored technical lead about the correct final upscroller.
The newly acquired official watch HTML contains a valid player JSON response,
the uploader identity, the 7 February 2026 publish timestamp, and an English
auto-caption track. Its description links the original production and a
general tools video; it does not provide an effect-source download.
Piper is a reverse engineer here, not a credited Hat coder.

The [Trident talk upload](https://www.youtube.com/watch?v=tqX42YoncaA)
likewise has a valid player response and English auto-caption track. Its
watch metadata has a 14 February publish timestamp, while the description
states a 13 February release. Neither date supplies the missing spoken
algorithm. The already retained March article is the source for its known
general IRQ example.

The retrieval distinction matters:

- The official legacy caption-list endpoint returned HTTP 200 with an empty
  body, even though watch-player metadata exposes a track.
- Both published track URLs and their JSON-format variants returned HTTP 200
  with **zero bytes**: four additional retained responses.
- A normal read-only request to each watch page's own transcript endpoint,
  using its published UI parameters, returned HTTP 400,
  **`FAILED_PRECONDITION`**. Both complete 274-byte error bodies and the exact
  request bodies are retained. Retrieval stopped there; no login or
  video/audio download was performed.

Thus HTTP success does not establish transcript contents, and these results
do not prove that no captions exist. No spoken technical detail was inferred
from the video title, description, neighboring comments or empty response.
An auto-generated transcript would also need checking for register names,
addresses and attribution before becoming a reliable mechanism account.

## What remains attributable

The live [Aloft creator-submitted interaction note](https://csdb.dk/release/?id=259056&show=hidden)
still supports joystick-controlled movement for flipped Kefrens on side 2.
It does not explain drawing, buffering, layer composition or prepared input.
The [release page](https://csdb.dk/release/?id=259056) still contains peer
observations whose scopes were established in the earlier note. Trident's
account of a party explanation is not that explanation's content; HCL's
line-frequency observation is not a captured implementation trace.

The same applies to [The Hat's release page](https://csdb.dk/release/?id=259070):
peers who looked at code are not publishing the instructions by praising
the ending. The acquired Alfatech profile did not identify a source route
that closes this gap. The existing generic ghostbyte example is not evidence
that the final ending uses it.

The concrete next boundary is therefore still original code or actual
technical contents. For The Hat, retain the side-B disk identity from the
earlier note and locate/bind the ending through its original loader before
identifying screen/bitmap/sprite consumers and raster changes. No entry PC,
loader family or mechanism is guessed here. For Aloft, keep the side-2
interaction, three-layer pattern and bitmap-Kefrens scenes distinct until
their original instruction/data domains are identified. A usable creator
writeup or timed teardown transcript would be a separate, worthwhile input.
