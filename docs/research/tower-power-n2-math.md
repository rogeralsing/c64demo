# Tower Power N2: product tables and 3D math

N2 performs runtime 3D transformation with precomputed **products**, followed by orthographic projection. The table bytes are not complete animation frames. This note derives that distinction from the validated payload and executes the original generator and transform in flat py65 RAM. It complements [the packed-stream note](tower-power-depacker.md) and [the native binary ledger](tower-power-binary.md).

The input is `side2/n2.00%-100%-100%` from the 100% final release. Its reconstructed memory-image SHA-256 is `8e57093143f46a8db18468210582b25969513e7409f77b649198c05901969540`. The original native loader has now reached N2 entry `$2034`: all **9,793 established output bytes** match the offline reconstruction, with no address exclusions. That receipt is `build/research/tower-power/n2-live-01/n2-comparison.json`; the raw capture is `ram-n2-entry.bin`, SHA-256 `9dd322037e48548ca557d3d20138a48a282b648d261a1f9e63928ee935a736e0`. This establishes the loaded payload, independently of the isolated math checks below. Native screenshot identity and displayed timing belong to the binary ledger.

## The 16 KB product table

Initialization calls `$30F4` from `$284A`. The generator reads 64 magnitude seeds at `$47C0..$47FF` and produces 64 pages at `$8000..$BFFF`: one seed per page, one biased coordinate per byte.

Every literal seed matches this expression exactly:

```text
seed[i] = floor(255 * cos((i + 1/2) * pi / 128) + 1/2),  i = 0..63
```

The first values are `255,255,255,254`; the last are `22,16,9,3`. This is a mathematical description matching all 64 bytes, rather than evidence of which source-language expression the author used to create them.

Coordinates use offset binary: byte `b` represents approximately `b−128`. The exact generated byte for magnitude `s` is:

```text
b >= 128:  floor((b−127) * s / 256)
b <  128:  −1 − floor((128−b) * s / 256)
```

Results are encoded modulo 256. The upper half is built by repeatedly adding `s` to a 16-bit accumulator and storing its high byte. The lower half restarts the accumulator, walks downward, and complements each high byte. The original generator's entire **16,384-byte** output matches the closed form. Its SHA-256 is `5e7ed80eace62cc50cc0a965ca76ee8c987c2a38e17b7636290aff0195c48c31`.

This is Q8-like table multiplication, with a maximum coefficient of `255/256`. The asymmetric rounding is intentional machine behavior. Replacing it with a generic signed multiply followed by a shift would not reproduce every output byte.

## Angle selection and self-modifying arithmetic

`$3140` reads three angle bytes at `$2A23..$2A25`. Each has 256 positions per turn, about 1.40625 degrees apart. The cosine samples lie half a step away from the cardinal axes: angle byte `a` corresponds to the coefficient at `(a+1/2) * 2*pi/256`.

The page selector folds the low six bits into the quarter wave:

```text
page = a & 63
if a & 64: page = page XOR 63
negative = (a & 192) is 64 or 128
```

The signed seed selected this way matches the rounded half-step cosine for all 256 angle bytes. Repeating the selection for `a+64` gives the quadrature coefficient, `−sin(angle)`.

Instead of branching on coefficient signs for every vertex, the patcher changes the high bytes and ADC/SBC opcodes in `$327C..$32C5`. These are ordinary indexed table operations: `$79/$7D` are ADC absolute,Y/X and `$F9/$FD` are SBC absolute,Y/X. Sign and quadrant work therefore happens once per transform call. Each source record then uses **12 product-table reads**, four per plane rotation.

The initial angle bytes are zero and their initial increments at `$2A26..$2A28` are `7,6,3`; `$21E4..$21FF` adds them before calling `$3140` at `$2202`. These are initial control values, not a native animation-period claim.

## Three plane rotations; no perspective divide

Name the signed source components `A`, `B`, and `C` in table order `$4600`, `$4650`, `$46A0`. Ignoring byte rounding and carry corrections, the transform has this structure:

```text
u = A*cos(alpha) − C*sin(alpha)
v = C*cos(alpha) + A*sin(alpha)

depth = v*cos(beta) − B*sin(beta)
w     = B*cos(beta) + v*sin(beta)

h = w*cos(gamma) − u*sin(gamma)
t = u*cos(gamma) + w*sin(gamma)
```

Thus it rotates one coordinate plane, rotates the intermediate result with the remaining coordinate, and finally rotates the screen plane. Axis names and screen orientation are conventions; the actual input/output addresses fix the behavior.

The routine stores an intermediate depth at `$33BB`, but **does not use depth to rescale the screen coordinates**. There is no reciprocal lookup or divide by camera distance in this path. It centers values around byte 128 and uses fixed shifts: horizontal output is the final biased `h` byte shifted right twice; vertical output is the final biased `t` byte shifted right once. Depth is also shifted right once. The horizontal coordinate is 0..63 logical multicolor pixels, spanning 0..126 physical pixels; the vertical coordinate is 0..127 rows. The different shifts compensate for multicolor pixels being two physical pixels wide.

For exact results, the displayed equations are insufficient. The original code chains binary ADC/SBC carry across terms and outputs. In particular, depth's LSR supplies carry to the next component, and the two horizontal LSRs leave a carry used by the next source point. The [analysis script](../../research/tower-power/n2_math.py) models those carry transitions explicitly; it does not round the real-valued equations and call that an exact reference.

## Forty transformed mesh points become eighty

The default 150-edge table references exactly vertex IDs `0..39` and `50..89`. The first forty literal records form four ten-point latitude rings, as recorded in `static/n2-geometry-candidate.json`.

The routine writes the first half and generates its partner with XOR:

| Component | First-half base | Partner base | Partner value |
|---|---|---|---|
| Horizontal | `$32F3` | `$3325` | `h XOR $3F`, or `63−h` |
| Vertical | `$3357` | `$3389` | `t XOR $7F`, or `127−t` |
| Depth | `$33BB` | `$33ED` | `d XOR $7F`, or `127−d` |

The partner index is 50 larger, leaving a gap between the two groups. Mirroring occurs after integer transformation and shifting, so its exact centers are 31.5 logical horizontal pixels and 63.5 vertical/depth units.

The loop actually processes **41 records**. Record 40 is `$FF,$FF,$FF`, producing additional outputs at IDs 40 and 90; neither is referenced by the default 150 edges. The following zero Z byte terminates the loop. It would be inaccurate to describe all 41 records as latitude-sphere vertices, or to describe the record as unused in every possible effect mode without inspecting those modes.

## What was executed and checked

Run from the repository root using the existing isolated py65 environment:

```sh
build/research/tower-power/cpu-venv/bin/python research/tower-power/n2_math.py
```

The harness executes original `$30F4..$313F` and `$3140..$32F1` instructions, with a synthetic caller supplying a normal return address. No algorithm routine is replaced. It checks:

- All 16,384 product cells against the closed form, plus all 256 signed angle selectors against the cosine description.
- Every first-half and mirrored output for 1,021 distinct poses: all 256 values of each single axis with the others zero, plus 256 triples `(7*k,6*k,3*k)` modulo 256.
- All 41 source records in each pose: **41,861 transformed pairs**, produced during **2,375,642 original instructions** including table generation.

The receipt is `build/research/tower-power/static/n2-math/math-validation.json`; the generated product table is saved beside it. This is finite pose coverage, not all `256^3` angle triples. It validates the stated math against the machine code, not disk transport, VIC output, full face adjacency, or a native frame budget. The result supports a concrete distinction: N2 spends substantial RAM on reusable multiplication tables while calculating its transformed coordinates at runtime.
