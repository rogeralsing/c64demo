# Nine: native Device raster cells and alignment families

Two naturally selected Device passes now match the released generated code: **146 monitored stores each**, with 21 cell starts exactly 63 emulated cycles apart in the observed PAL run. The `$3000` and `$3400` families place their first two color/mode writes one monitor cycle apart, then converge to the same later write positions. Each traced run ends with exactly the same captured C64 CPU, physical RAM and complete VIC state as its untraced replay. **The whole machines are not identical:** drive-state differences are retained and source-mapped below.

This is a native store/control/restoration proof, not a reconstructed Device image, a physical-bus-phase calibration or coverage of every VIC revision. The [author's explanation](https://www.linusakesson.net/scene/nine/explanation.php) describes stabilizing sprite DMA, using invalid-mode/ghostbyte graphics, and hiding sprite-pointer-table changes on repeated pattern rows. This pass binds particular generated bytes to their original native execution.

## Inputs and the path into Device

The original PRG SHA-256 is `a257fa0436bc0d97fbeaa906c55489786a26ee6a9213aa3fd0d8e21f9612d839`. The [earlier byte proof](nine-binary.md) independently reproduces the unpacking, nine relocated blocks and all three generated families. Its 64 KB generated fixture is SHA-256 `507a2c6b869db6c55a7730eae18bd5f1688415a87b4071577c85ce0e21cb995b`. This pass reuses that result and executes no CPU fixtures or matrices.

Device comes **after** the first [character-digit stage](nine-character-path.md). The main script waits at `$85EB` for `$3E>=127` and `$35=$40`, performs one more update at `$85FA`, then flips control bit `$04` at `$85FD`. That selects the crunched/ghostbyte producer rather than `$9051`'s ordinary digit producer. Publication is `INC $CD` at `$904E`; the top-level IRQ consumes it at `$9A09` and installs `$9B00`.

The native run first reaches `$9B00` at clock 110,919,386, raster 9/cycle 11. Its first later `$9BB1` call is clipped to stop row zero, so it cannot demonstrate a repeating pattern or both pointer switches. That first call remains separately captured: 92 observed cycles through its call/return, then 110 more through restoration. The canonical proof instead waits naturally for a full stop-row-20 pass. No PC, geometry or original code was supplied to force either case.

## Selection is detector result plus horizontal phase

The families are not simply three interchangeable X alignments. `$82E2` calls the hardware detector at `$9900`. Carry set leaves baseline page `$34` in the immediate operand at `$8DD4`; carry clear patches it to `$38`. `$8DD3..$8DE1` then subtracts four pages whenever `$62&7` is nonzero. `$62` was computed as `$63&7` and also supplies `$D016` fine scroll.

| Detector result | Fine scroll zero | Fine scroll nonzero |
| --- | --- | --- |
| Carry set: baseline `$34` | `$3400` | `$3000` |
| Carry clear: baseline `$38` | `$3800` | `$3400` |

The actual jump operand is `$9BD6/$9BD7`; the checker reads it rather than inferring a family from the picture. Both captured runs use the current PAL model's baseline `$34`: fine phase **5 selects `$3000`**, and phase **0 selects `$3400`**. `$3800` remains source/CPU-proved, without a native pass in this note. Observing it naturally would require the other detector outcome, rather than editing the family operand.

In the `$3400` family, cell offsets `+2/+3` are two NOPs instead of the `$3000` family's `BIT $00`. Its `+0F` store is absolute `STA $D021`, while `$3000` uses indexed `STA $CFB1,X` with `X=$70`. The instruction lengths and store PC offsets remain the same; their read/write scheduling differs. The previous CPU-only instruction-start table must not be substituted for native bus timings.

## What the captured cells actually store

At each call, the original prelude sets `X=$70` and `Y=RAM[$67]`. The captured shadows are `$65=$02`, `$66=$1A`, `$67=$04`. A normal cell loads those shadows and emits:

| Store PC within cell | Literal target/value | `$3000` monitor cycle | `$3400` monitor cycle |
| --- | --- | ---: | ---: |
| `+06` | `$D021 ← $02` | 24 | 25 |
| `+0B` | `$D011 ← $1A` | 31 | 32 |
| `+0F` | `$D021 ← $1A` | 38 | 38 |
| `+12` | `$D021 ← $04` | 42 | 42 |
| `+15` | `$D021 ← $70` | 46 | 46 |
| `+18` | `$D011 ← $70` | 50 | 50 |
| `+1D` | `$7FFF` pattern byte, or `$D018` table selector | 12 of next raster | 12 of next raster |

These are **zero-based cycles printed by the monitor's store checkpoints**. They are not labeled instruction starts or hardware Phi2 bus phases. In particular, the `$1A/$70` background writes contribute colors through their low nibbles; a literal byte containing mode bits is not a new palette entry.

For both observed families, the first store of cells 0..20 occurs at rasters **27..47**, with all 20 consecutive clock deltas exactly **63**. This establishes repeating cadence for these captured passes, not a general 50 Hz update rate or every possible sprite/DMA configuration.

Cells 2 and 17 replace a pattern update with `$D018=$50/$60`. In the captured bank-$4000 configuration, these select sprite-pointer tables **`$57F8` and `$5BF8`**, whose bytes are recorded in the receipts. The four prepared column sprites retain members 0,2,4,5: their pointers change from `$91/$95/$99/$9D` to `$92/$96/$9A/$9E`. The main program's separate pointer setup and `$D017` crunch sequence are connected to actual native `$D018` stores here; a full sprite-fetch/pixel reconstruction is still outside this proof.

The `$3000` switches are monitored at clocks **112,512,846** and **112,513,791**, raster 30/45, cycle 12. The `$3400` switches are exactly one PAL frame later, at **112,532,502** and **112,533,447**, at the same raster/cycle. Both source pattern rows repeat the preceding row, so the skipped ghostbyte update is redundant. The monitor confirms the pointer writes; the independent byte proof establishes the duplicate-row relationship.

## Stop-row patches and complete restoration

Each family contains 21 cells of 32 bytes followed by an RTS. The main code's `$70/$71` pointer chooses an active stop cell. Before this full pass it points to **`$3280`** or **`$3680`**, row 20 of the selected family. Exactly two cell bytes are patched:

- `+18`: `$8E` (`STX $D011`) becomes `$8F` (`SAX $D011`). With A=`$1A`, X=`$70`, the closing write is `$10`.
- `+1B`: `$A9` (`LDA #pattern`) becomes `$60` (`RTS`), skipping that final cell's pattern update.

Thus this is 20 complete cells plus one closing cell, **not 21 pattern updates**. Its store total is 84 to `$D021`, 42 to `$D011`, 18 to `$7FFF` and two to `$D018`: 146 in all. Every expected PC, opcode, effective target and literal value matches the trace. The final SAX is at `$3298` or `$3698`.

Before the call, all 2,019 generated bytes match the previously proved families except those **two identified temporary bytes**. The generated region is unchanged through the call. Physical RAM across `$9BB1→$9BB4` matches the independent stack/store prediction over all 65,536 bytes: the JSR's two return-address stack bytes and the final `$7FFF` pattern value are the only permitted writes. SP returns unchanged, with A/X/Y=`$1A/$70/$04`.

`$9BB4` is before restoration. The original `$9BD8..$9BE2` code restores `$A9` at `+1B` and `$8E` at `+18`; `$9BE4` is the first safe post-restoration boundary. All 2,019 family bytes then match their original baseline exactly. Every physical RAM byte also matches the after-call state with only those two opcode restorations; no broad mutable-code mask is used.

| Captured call | Before `$9BB1` | Return `$9BB4` | Restored `$9BE4` | Observed intervals |
| --- | ---: | ---: | ---: | --- |
| `$3000` | 112,512,604, R26/c22 | 112,513,976, R48/c8 | 112,514,063, R49/c32 | 1,372 cycles; then 87 |
| `$3400` | 112,532,260, R26/c22 | 112,533,632, R48/c8 | 112,533,719, R49/c32 | 1,372 cycles; then 87 |

These intervals include real emulated scheduling and the original prelude/return. They are neither isolated CPU instruction totals nor measured whole-effect frame costs.

## Traced versus untraced: exact C64 state, unequal drive state

For each family, the operator restores the same before-call VSF, resumes to the same `$9BB4` breakpoint with no store traces, and saves the control. The traced pass uses only four store checkpoints, with no attached automatic commands. **The complete `MAINCPU`, `C64MEM` and `VIC-II` payloads are byte-identical**, including VIC drawing buffers and internal fetch state. Every other snapshot module is compared too; none is omitted or normalized.

The first comparison differs in four drive bytes:

| Module / payload offset | Traced → control | Official VICE 3.10 field |
| --- | --- | --- |
| `1541VIA1D0`, 22 | `$E0→$C0` | Packed CA2/CB2/CB1 line state; changed bit `$20` |
| `VIA2D0`, 22 | `$60→$40` | Same packed line-state field |
| `DRIVE8`, 27 | `$02→$00` | Low byte of `GCR_head_offset` |
| `DRIVECPU0`, 43 | `$A1→$A2` | Low byte of the drive CPU's 64-bit `stop_clk` |

The second comparison has different drive execution state: its drive CPU clock is **114,218,128→114,218,132**, PC **`$EC14→$EC17`**, status **`$21→$A1`**, last-opcode information **`$A6→$BD`**, stop clock **114,218,128→114,218,129**, and last-data byte **`$04→$FF`**. Both VIAs' T1 and T2 counter values are four lower in the control. Every differing payload byte and complete decoded source-field value remains in the receipt. No CIA module differs in either comparison.

The field mapping is pinned to the official [VICE 3.10 source archive](https://sourceforge.net/projects/vice-emu/files/releases/vice-3.10.tar.gz/download), SHA-256 `8e5bac18cbcb9f192380ad3ef881f8790f5b75c41d7b3da65d831985d864d6d1`: `src/core/viacore.c:1952–1979`, `src/drive/drive-snapshot.c:149–184`, and `src/drive/drivecpu.c:560–572`. Source members and hashes are preserved beside each receipt.

There is a relevant serializer asymmetry: the VIA writer combines CB1 input/output into bit `$20`, while its reader tests CB1 input/output from bits `$10/$08` (`viacore.c:2149–2153`). That is consistent with the first round trip losing the combined CB1 bit. It is not proof that this accounts for every drive difference. The second control is genuinely four drive cycles ahead, not merely a diagnostic byte with a different spelling. The exact contribution of snapshot restoration and monitoring to these peripheral differences has not been isolated.

Accordingly the receipts mark the **scoped C64 trace/RAM/VIC/restoration proof passed**, and explicitly mark **whole-machine equality false**. The 63-cycle and literal-store conclusions are bounded to the observed C64 execution; the control does not establish that tracing or snapshot restoration leaves every emulated peripheral unchanged.
