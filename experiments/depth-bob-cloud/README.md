# Depth-sized bob cloud and allocated glyphs

An original counterpart to **Next Level**'s `bobvector` pipeline: prepared
3D point positions and depth-size buckets drive live character-based software
bobs. The C64 allocates glyphs on first touch, OR-merges overlapping stamps,
clears only the scene's possible matrix cells and publishes complete font/matrix
pairs. No original code, point stream, artwork or screen poses are included.

```sh
sh build.sh
sh run.sh
python3 verify.py
```

Build runs the tracked Python producer, then Java/KickAssembler through the
shared helper. Run uses normal-speed PAL VICE. Verification needs Python3/Pillow,
the tracked root monitor helper and Colodore palette. Everything generated is
under ignored `build/`; a fresh checkout rebuilds its required inputs. No network,
research cache or sibling repository is needed.

## Prepared geometry, live rasterization

`prepare.py` constructs an own **56-point surface lattice**, the boundary of a
4×4×4 grid. Host yaw/pitch/roll rotation and perspective produce 64 poses in a
160×128-pixel point window. Nearer points choose larger disks from nine sizes,
1–9 pixels. Records are grouped by size and ordered by character address and
pixel phase. The scene stream is **7744 bytes**: 64 nine-byte bucket headers and
64×56 pairs of X/Y coordinates. It contains no animation bitmap.

The C64 decodes each bucket and stamps every point at its supplied pixel
position. It does not calculate 3D rotation, projection or depth. A small static
legend shows all nine disk sizes; those same original disk shapes are used by
the live stamps. Assembly emits **720 reusable pattern bytes** covering nine
sizes and eight horizontal pixel phases. Vertical placement and character-row
crossings are handled at runtime.

Each nonzero source byte identifies a screen cell and a glyph row. On the first
touch of an empty cell, the C64 allocates a private code, initializes all eight
glyph rows and stores the code into the matrix. Further rows/points reuse that
cell's glyph and OR their bits into it. Overlapping disks form a same-ink union;
there is no opaque depth sort or independent per-bob palette. The depth cue is
the prepared projection and disk size.

Code 0 is blank, codes 1–191 are private, and codes 192–255 hold immutable original
title, border and legend glyphs. Allocation stops with a red border before it
could enter the shared range. The fixed dataset uses 69–96 private cells, so
arbitrary overload input is outside this normal-run proof. Unreferenced private
glyphs may retain older bytes until their next allocation; the screen never
references those stale slots. First-touch initialization makes reuse safe.

## Selective clears and coherent publication

The producer derives the union of cells that any prepared point can ink. That
map contains **148 cells**, with every static title/border/legend cell excluded.
At startup the C64 reads this map and emits two clear routines: one direct
`STA abs` per selected cell, followed by RTS. The **890 generated bytes** clear
the matrices, not the complete fonts or complete screen.

Before rendering into the back pair, its generated routine writes zero to those
148 cells. The allocator then starts again at code 1. The previous complete front
font/matrix pair stays unchanged while the back pair is cleared and stamped.
The fitted [`display.asm`](../prepared-fragments/display.asm) is imported
unchanged for publication at the next top border and a complete scanout wait.
Our own hires palette, base matrices and initial fonts replace its generic
initial display settings. No shared source is modified.

The pairs are font `$2000`/screen `$0400` and font `$2800`/screen `$0C00`.
Both matrices use the same fixed color RAM: green point ink, cyan title, blue
border and green disk legend. This is software drawing into character glyphs;
it does not use sprites or a bitmap background-restoration engine.

## Native evidence and cadence

The verifier independently composes 3×3 rotation matrices and reproduces every
prepared coordinate and depth bucket, without importing the producer. A separate
pixel-center disk classifier builds point coverage. It predicts first-touch
code allocation, glyph uniqueness, OR union and complete matrix/font contents,
including unused and stale glyph storage across both buffers.

Normal PAL VICE execution passes **66 publications**, all 64 poses and wraparound.
All **3696 actual point-stamp calls** match their size/X/Y schedules. Each pose
has 22–44 cells shared by multiple points and 6–107 genuinely overlapping pixels.
Both complete 2KB fonts and 1KB matrices match before/after every clear, after
stamping and after publication. Clears preserve both fonts and the whole front
pair. Shared glyphs, blank code 0, prepared inputs and generated code remain
unchanged. All **6,893,568 full-screenshot pixels** match.

Startup generation takes **85,136 native clocks**. Each selective clear takes
**606 clocks** including its caller/return. Rasterization takes 96,097–107,567
clocks including display IRQs and VIC stalls. Publications occur every **6–7 PAL
fields**, averaging 6.6154 fields, about **7.56 updates/second**. This is a bounded
teaching implementation, not the original production's speed. The owned VICE
process exits normally with code 0.

Evidence is in `build/verification/proof.json`, with the generated clear bytes,
point trace, complete images and sampled GIF. `depth-bob-cloud.gif` uses uniform
160ms sample playback and does not represent native cadence. A failed rerun
removes the current success receipt. Physical-hardware behavior, arbitrary
streams and allocator overload are separate from this normal fixed scene.

## Source mechanism and own differences

The archived sources were read at author revision
`57643d53a97cdf38778958d8ebf99341315f834e`:
[`coords.c`](https://github.com/bboxy/next-level/blob/57643d53a97cdf38778958d8ebf99341315f834e/parts/bobvector/coords.c)
performs host transforms, depth sizing and bucketed stream preparation;
[`sbf.asm`](https://github.com/bboxy/next-level/blob/57643d53a97cdf38778958d8ebf99341315f834e/parts/bobvector/sbf.asm)
consumes that stream, dynamically allocates/OR-merges glyphs, specializes partial
character chunks and generates selective screen clears. See the owning
[source survey](../../docs/research/lines-and-vector-fill.md).

The original has 98 prepared cube-surface points, a 146-frame stream with a later
128-frame loop, different packed records, graphics and specialized size paths.
Our 56-point cage, 64 poses, stream format, disk shapes, allocation budget, layout
and byte-wise stamping are own choices. Source labels containing “and” do not
change the observed OR-compositing contract. This example covers that distinct
point-cloud/glyph-allocation pipeline; it is not a generic masked-bob alias or
a claim of C64 runtime 3D geometry.
